# Ring Explorer: app spec (PRD)

Version P1, signed 2026-11-10. Full tier: a person opens it in a browser.

Whose words (the owner, 2026-11-10): "I want in my browser a full app that allows me to go and see the design, internal, PCB, etc. and have EVERYTHING so I know what I'm building myself".

The four needs, the owner's answers on the card of 2026-11-10:
- Who: "Me, then a build partner".
- Today: "Chat only, I cannot see it".
- Version 1: "See everything (Recommended)".
- Where: "On this Mac only (Recommended)".

| Field | Answer |
|---|---|
| Purpose | One place in the browser to see the whole ring design. Done means: from the first screen the owner reaches every area of the design and every part, sees it, and reads in plain words what it is. Checked by the journeys of `docs/JOURNEYS.md`. |
| Success criteria | (1) From the home screen, any part of the ring is reached in 3 clicks or fewer. (2) Every line of the ring parts list (77 today) opens a part card with: what it is in plain words, why it is in the ring, maker order code or the named open action, and its evidence level. (3) For each of the 8 areas (look, inside, electronics, board, parts, behaviour, case, open items) the app states one of: done, in progress, not started, waiting on a supplier, and that state matches the project files. (4) The owner can rotate the ring and open it layer by layer without reading any text. (5) A build partner downloads the complete file set from one screen. |
| Pivotal loop | See the ring, open it up, click a part, understand it. The 3D ring with its inside is the core; every other screen hangs off a part or an area of it. |
| Residual | `Residual: open critical/HIGH rows + unmet REQUIRED rows + red gate checks + journeys not passing (of every journey in docs/JOURNEYS.md) = N` |
| Test plan | Unit: the data collector (design files to JSON), in `explorer/tests/unit/`. Integration: the collector against the real design folder. End-to-end: one test per journey with headless Playwright, seen red at scaffold. Smoke: the server starts and every screen loads with zero console errors. Contract: the data bundle's schema. Regression: one test per bug the owner reports. Functional, acceptance: the journeys. Performance: first load and 3D frame time against the budget. Mutation: each check proven to fail once. Runner: `npm test` and `npm run journeys`, both exit non-zero on failure. |
| Users + audiences | Audience 1: the owner, non-technical in hardware, wants to see and understand. Audience 2, later: a build partner (design firm or factory), technical, wants exact files and order codes. One app, two depths: plain words first, exact data one click below. |
| Access + identity | `Access: PUBLIC - hosted as a Vibe app on <platform>, reachable by anyone with the address, no sign-in; owner 2026-11-10: "I need to have the app as a vibe app on <platform> publicly accessible". Before that: LOCAL first - runs on localhost on the owner's Mac, owner: "On this Mac only (Recommended)"; THEN ONLINE to share, owner 2026-11-10: "all I can then share to someone (after putting online)"`. The build must also run as a hosted static app. Who may open the online copy (private to invited people, or anyone with the link) is decided at the hosting step, before anything is published. Text before this change: no hosting, no sign-in. The <platform> identity model does not apply to a page served only on this machine. The partner receives files, not access. |
| Job & role | Today the owner follows the design through chat messages and cannot see the object. He decides: the look, the trade-offs (size, battery, controls), what to send to a partner. At a glance he needs: what the ring looks like, what is inside, what is finished, what is open. |
| Screen map | See "Screens" below. 9 screens, each with purpose, see, do, decide. |
| Levels of analysis | Whole ring, area (8 areas), part (77 lines, 146 parts), document (source file). |
| Interaction model | Fixed explorer, not a composable investigation tool: the same screens every time, with the current design in them. Free 3D rotation and a part search are the two open-ended controls. |
| Data sources + freshness | One source: the project folder `design/` plus `requirements.md`, `feasibility.md`, `partners.md`. Freshness: a command `npm run collect` rebuilds the app's data from the files; the app shows when the data was built and from which git commit. No live link to the outside world. |
| Data architecture | The app holds NO state of its own: it is read-only. The source of truth is the design files under git. `state-home: none - read-only viewer; every value comes from the design files`. The org warehouse does not apply: nothing is written. The data bundle (`explorer/public/data/`) is generated and can be deleted and rebuilt at any time. |
| Client data-flow + reactivity | The app loads static JSON and 3D files built by the collector. No server state, no cache to invalidate. `Perf-budget: first-paint 1500ms · interaction 100ms · route-read 300ms cold / 100ms warm`. `Reactivity: n/a - no value changes while the app is open; a rebuild plus refresh shows new data`. |
| Config/control surfaces | n/a: version 1 has no settings. View switches only (finish colour, screen state, exploded or assembled). |
| External services | None at run time. The 3D library loads from the local install, not from the internet, so the app works offline. |
| Foundation / base + seed set | Base: to price at the architecture step against the org starter (scorecard in `references/base-decision.md`). Lead's proposal: build fresh as a local static app, since the org starter targets hosted apps with records and sign-in. Seeds: (1) the 3D look viewer being built now in `design/look/viewer/` (supplies the 3D rendering and materials; becomes the Look screen); (2) the design files themselves (supply all content); (3) the owner's reference picture of a black ring with a screen (supplies the feel). |
| Capability routing & AI map | Every capability is an app view. No workflow, agent or AI task: the app shows files and computes nothing a <platform> primitive would do better. Proposed AI opportunity, NOT in version 1: a "ask about this part" chat on a part card, routed to a <platform> agent with the design files as knowledge. |
| Technology choices | Runtime: Node 24 (installed on this Mac). Framework: React with Vite, three.js for 3D. Data: static JSON, GLB and SVG files built by a Python collector that reuses the project's existing tools (build123d, KiCad command line). Hosting: none; a local server on localhost. Decided by: local-only use, the 3D core, and the tools already on this Mac. |
| Commodity blocks | 3D rendering: three.js (not written by us). Wiring diagram and board pictures: exported by KiCad's own command-line tool as SVG. Tables and search: a small library chosen at the architecture step. PDF viewing: the browser. Sign-in, payments, email, storage, i18n: n/a, none needed. Data store: none. |
| Visual authority | The owner's reference picture: glossy black object on white, calm, premium, few words. The app's look is picked by the owner from rendered boards (layout first, then style) before any screen is built. |
| Quality bar | The owner's words on the ring apply to the app: it must look good "like the ring design I gave". Each screen is judged against the picked boards. |
| Run-mode matrix | n/a: not a shipped bundle. One mode: Chrome or Safari on this Mac, localhost. |
| See it or know it | Everything is SEE: this app exists because the owner cannot see the design today. |
| Non-goals | No editing of the design in the app. No decisions saved in the app (version 2). No ordering or supplier tracking (version 3). No hosting, no sign-in, no phone layout. No AI chat in version 1. None of these was asked for by a named person. |
| Review contract | The owner judges every screen on localhost. Coverage: every screen, every journey. Delegation: allowed; builders work on separate files, one reviewer seat per quality, the lead judges the first screen itself. |
| Rollout | First user: the owner. Version 1 accepted when the owner has opened every screen and says it shows him what he is building. The partner view (file download) ships in version 1; partner-specific depth follows the partner's feedback. |
| Standing arbitrations | Sites are shown on localhost, never published. Headless tests only. Light theme for pages (owner's standing preference for web pages); to confirm for this app at the style pick, since the reference object is black. |

## Screens

| # | Screen | Purpose | The owner sees | The owner can do | Decision it serves |
|---|---|---|---|---|---|
| 1 | Home | The ring at a glance | The ring in 3D, its key numbers (size, weight, battery, hours, storage), and the state of each of the 8 areas | Rotate; click an area | Where do I look next; how far along is this |
| 2 | Look | The outside | The exterior in 3D with real materials, finishes, the screen lit, the ring on a finger for scale; while the look is not picked, the 3 options side by side | Switch finish, screen state, view; compare options | Which exterior do I want |
| 3 | Inside | What is in it | The ring opening layer by layer (glass, screen, board, cell, housing), every part highlighted on hover, cross-sections | Explode and reassemble; click a part for its card; search a part | Do I understand what each part is and where it sits |
| 4 | Electronics | How it is wired | The block diagram, the 8 pages of the wiring diagram, the chip's pin plan, the power budget, and the connection map: every connection between the boards and the parts (ring board, the two band circuits, cell, motor, joystick, charging pads, case pins, case boards) | Click a block to jump to its page and its parts; zoom a page; click a connection to see its two ends, its signal and the file that proves it | Is the circuit complete; what is still open; what do I solder to what |
| 5 | Board | The circuit boards | A board picker: the ring's main board, the two band circuits (per ring size) and the two case boards. For the picked board: its outline with every part placed, both faces, and its routed copper, one layer at a time; an honest state banner per board (routed and checked, or 'not finished: N connections open') | Pick a board; toggle faces and copper layers; click a part | Is each board ready to manufacture |
| 6 | Parts | Everything to buy or make | The full list: part, maker, order code, price, evidence, open action; totals | Filter (has code, made to drawing, needs supplier); open a part card; export CSV | What can I order today; what is blocked |
| 7 | Behaviour | How the ring acts | A simulated ring: button, joystick, light, vibration, screen; the firmware's states | Press and hold the virtual button, move the joystick, and watch the ring react per the firmware rules | Do I agree with how it behaves |
| 8 | Case | The charging case | The case in 3D with the ring seated, its parts, charge and transfer times | Rotate, open the lid, click parts | Is the case what I want |
| 9 | Open items and files | What is not finished, and every file | Supplier requests, bench tests, risks, the owner's past decisions with dates; every project file grouped by area | Open or download any file; download the full partner bundle | What do I do next; what do I send a partner |
