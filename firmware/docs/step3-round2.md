## 2. A late answer fragment after the 3 s timeout

- **Fix, parser.** Before a valid header the stream is searched byte by byte: a late answer of another request, or fragments without a header, are skipped (counted in `skipped`), not an error (`modules/ring_iphone/src/ripl.c:91`). The four bytes read as an id are searched again when they are not ours (`modules/ring_iphone/src/ripl.c:113`), and a "header" whose first attribute is wrong is searched again too (`modules/ring_iphone/src/ripl.c:126`): the end of a stale answer can make a false header with the first byte of ours (found by my own logic test `tests/iphone/src/test_iphone.c`, "05 00 00" case, before I wrote the second rule).
- **Fix, retry.** `modules/ring_iphone/src/rip.c:126`: a request that timed out, got a wrong answer or whose write failed goes to the front of the queue once (`fetch_retries`); a second failure is given up (`fetch_failed`). Called from the timeout (`modules/ring_iphone/src/rip.c:319`; round 2 first wrote :318, which is the counter line above the call), the answer error, the write callback and the write start.
- **Logic test:** `tests/iphone/src/test_iphone.c:163` (a stale answer then ours, in every fragment size from 1 byte up; the middle of a stale answer; the stale-end false header; only a stale answer never completes; another command id is skipped).

The stand-in's outgoing answers go through one queue so two answers never interleave (`tests/bsim/iphone/host_app/src/main.c:349`). The ring checks (`tests/bsim/iphone/ring_app/src/main.c:627`): `LOG:4248`, `LOG:4249`, `LOG:4250`, `LOG:4251`. The stand-in's own record: `LOG:4277`, `LOG:4278` (its log line: `LOG:4273`).

## 6. A link that ends during discovery

- **Test, scenario D** (`tests/bsim/iphone/ring_app/src/main.c:657`, `tests/bsim/iphone/host_app/src/main.c:1357`): the stand-in ends the link 60 ms after the ring subscribed to the Data Source (`tests/bsim/iphone/host_app/src/main.c:324`), while the ring is still looking for the Media and Current Time services, stays away 3 s, then reconnects. Stand-in side: `LOG:4321` (its log line: `LOG:4311`), `LOG:4322`. Ring side: `LOG:4292`, `LOG:4294`, `LOG:4295`, `LOG:4298`, `LOG:4299`. The ring's counters in that run: `LOG:4297`.
- **What the test showed, and the fix.** The first run of D (`console-r2-second.txt`) passed every check about the next session (the kit's discovery manager frees itself when the link ends: the three services were found) but failed the check "no service was reported missing". I added a diagnostic line; the next run (`console-r2-third.txt`) printed `RING INFO D: missing 0/1/0, dm_errors 0, dm_stale 0`: the Media service was counted as "not found" in the session that had ended. The Bluetooth host ends a running discovery when the link goes down and calls the discovery's callback as "not found" before this module's own disconnect callback runs; the same callback could also have moved the phase of the next session. Fix, first attempt: every discovery carries the number of its session and a stale session's answer is dropped; it did not change the result (which suggests that the callback comes while the session is still the current one). Fix that worked: the answer is also dropped when the link is no longer connected (the link is asked), counted as `dm_stale`: `modules/ring_iphone/src/rip.c:678`, `modules/ring_iphone/src/rip.c:952`, `modules/ring_iphone/src/rip.c:675`. The review's worry that the discovery manager would stay busy and the service be skipped for the whole next session did not occur in this test: the manager was free in the next session and no retry was needed (`dm_errors` 0).
- **Limit:** the drop comes after the Notification Center discovery and before the Media discovery has finished; a drop during the first (GATT service) or the last (Current Time) discovery is not tried. No broken copy for D (not asked for): the fix is checked by the counters and the three-services check, and the "missing 0/1/0" run above is the before state.
