## 3. Versioning and downgrade protection

- Image version set by imgtool: [F] https://docs.mcuboot.com/imgtool.html, `r/p1.txt` line 182: "-v, --version TEXT [required]"
- VERSION file: [S] Nordic image-version page (https://nrfconnectdocs.nordicsemi.com/ncs/latest/nrf/app_dev/bootloaders_dfu/mcuboot_nsib/bootloader_dfu_image_versions.html, search summary): "Since nRF Connect SDK 2.5.0, the recommended way to set an application's version is a VERSION file, not the older CONFIG_MCUBOOT_IMAGE_VERSION option. You can still set the version in Kconfig with CONFIG_MCUBOOT_IMGTOOL_SIGN_VERSION, but a VERSION file is the recommended approach." Example value [S]: `CONFIG_MCUBOOT_IMGTOOL_SIGN_VERSION="0.1.2+3"`.
- Conflict: [S] DevZone 126847 (https://devzone.nordicsemi.com/f/nordic-q-a/126847/inquiry-on-modifying-software-version-string-for-matter-product-in-ncs-3-1-1/562363): on NCS 3.1.1 the version stayed `3.0.0+0` after setting `CONFIG_MCUBOOT_IMGTOOL_SIGN_VERSION`. No resolution found.
- Software downgrade prevention: [F] https://docs.mcuboot.com/design.html, `r/p2.txt` line 1607: "Downgrade prevention is a feature which enforces that the new image must have a higher version/security counter number than the image it is replacing, thus preventing the malicious downgrading of the device to an older and possibly vulnerable version of its firmware." Line 1615: "This feature is enabled with the MCUBOOT_DOWNGRADE_PREVENTION option. In this case downgrade prevention is only available when the overwrite-based image update strategy is used (i.e. MCUBOOT_OVERWRITE_ONLY is set)."
- Hardware rollback protection: [F] same page, lines 1622-1623: "Each signed image can contain a security counter in its protected TLV area, which can be added to the image using the -s option of the imgtool script." Line 1637: "the MCUBOOT_HW_ROLLBACK_PROT config option. When enabled, the target must" (the counter must live in non-volatile trusted storage; the target provides it).
- My reading, not a source: the software downgrade check is tied to overwrite-only mode, so it does not apply if swap mode is used. Check against the build config before relying on it.
- Swap mode: [F] `r/mcuboot_text.txt` line 321-322: "Note: This mode is not recommended for use and swap-using-offset or swap-using-move are recommended instead." This refers to swap-using-scratch. [F] design.html line 381: "Please note that the swap-using-offset algorithm is preferred over swap-using-move". The two MCUboot pages differ in emphasis; both name swap-using-move as usable.
- Nordic's own downgrade rule for nRF54L: not found in a readable page.

## 4. Production programming of nRF54L series

- Programming command: [S] Nordic "Programming application firmware on nRF54L Series" (https://docs.nordicsemi.com/r/bYkE8evbjCoV6wV0tetlaQ/DH68569lcfhU1m6k0_5I0Q, search summary): `nrfutil device program --firmware <file_path> --options chip_erase_mode=ERASE_ALL` and then `nrfutil device reset --reset-kind=RESET_PIN`. Not checked against the page itself (bot check).
- Production guide scope: [S] "nRF54L Series Production Programming" (https://docs.nordicsemi.com/r/bundle/nan_047/page/APP/nan_production_programming/intro.html, search summary): aimed at NVM programming tool developers. "Some steps can be skipped, for example if the device has never been programmed and its NVM is fully erased, or if the device is unprotected." Also: "With access port protection disabled, data is written to the non-volatile memory (RRAM) using the standard Serial Wire Debug (SWD) Arm CoreSight Debug Access Port (DAP) protocol." Also: "KMU data and permission policies can be erased only by using the CTRL-AP erase all operation."
- Access port protection: [S] "Enabling device protection" (https://docs.nordicsemi.com/r/nIRZkb7fbawflqd9K7EVwA/3nnwhUVxV7Ixo18NKA3zzg): "If these registers have any value other than 0xFFFFFFFF, the device is protected." "Ensure all protections are configured before performing a reset if enabling APPROTECT or ERASEPROTECT." "If the device has activated both APPROTECT and ERASEPROTECT, it cannot be recovered without a proper software solution." Protection mechanisms listed for nRF54LM20A: SECUREAPPROTECT, APPROTECT, ERASEPROTECT (same page, search summary).
- Disabling APPROTECT: [S] "Disabling APPROTECT" (https://docs.nordicsemi.com/r/nIRZkb7fbawflqd9K7EVwA/LCp8mz_4bd4XX4EWuQDMFA): "If the device has access port protection enabled and is not erase protected, you can disable access port protection by using a Control Access Port (CTRL-AP) erase all operation." Consequence: a unit with APPROTECT set and ERASEPROTECT not set can be unlocked by erase-all. Production choice on this is for the team.
- ERASEPROTECT release: [S] forum only (https://devzone.nordicsemi.com/f/nordic-q-a/128209/request-for-nrf54l15-jtag-lock-unlock-procedure/567016): disabling ERASEPROTECT needs a key write from debugger and CPU. Nordic docs not found to confirm.
- KMU provisioning: [S] DevZone 126876 (https://devzone.nordicsemi.com/f/nordic-q-a/126876/ncs-3-2-1-single-slot-dfu-issue-with-nrf54l15dk/560471): flashing merged.hex alone left the board unresponsive; Nordic's fix was `nrfutil device x-provision-keys` to provision keys onto the KMU. No single documented flash-plus-provision command found.
- SWD programming with J-Link: [S] DevZone 128546 (https://devzone.nordicsemi.com/f/nordic-q-a/128546/nrf54lm20a-external-swd-programming-issue-and-lm20-dk-request/568384): J-Link Commander and Nordic Programmer failed on the same merged.hex on an external nRF54LM20A, while nrfutil succeeded through the same probe. Forum report.
- Gang programmers, programming houses, pre-programmed chips: not found in a readable Nordic page. Pages tried: the Nordic production guide and KMU page (bot check or search summary only).
- What must be written besides the application: [S] MCUboot and KMU provisioning (sections 2 and above). Bootloader and UICR contents for production not confirmed in a readable page.

## 7. Regulatory and Bluetooth SIG requirements

- EU, Radio Equipment Directive 2014/53/EU: [S] EUR-Lex (https://eur-lex.europa.eu/eli/dir/2014/53/oj/eng, not readable; search summary of Article 10): "Once compliance is demonstrated, the manufacturer issues the EU declaration of conformity and affixes the CE mark." - US, FCC: [S] FCC OET 63 (https://transition.fcc.gov/Bureaus/Engineering_Technology/Documents/bulletins/oet63/oet63rev.pdf, search summary): Bluetooth devices generally need FCC certification "prior to marketing"; testing alone does not need authorization. Official FCC page (https://www.fcc.gov/engineering-technology/laboratory-division/general/equipment-authorization) returned "Access Denied" (`r/s6.html`), not read.
- Bluetooth SIG: [F] https://www.bluetooth.com/develop-with-bluetooth/qualification-listing/ (`r/s7.txt` lines 1161, 1174, 1178): "ALL Bluetooth® Products must be qualified". "Your supplier or other member companies cannot qualify your products on your behalf. You must complete the Bluetooth Qualification Process for your product under your company's membership account." "A Product Qualification Fee will be required for the first product submission that includes a specific design."
- UN 38.3 (lithium cell transport): [S] UNECE Manual of Tests and Criteria section 38.3 (https://unece.org/fileadmin/DAM/trans/danger/publi/manual/Manual%20Rev5%20Section%2038-3.pdf, not readable; search summary): cells go through T.1 to T.6 and T.8, and non-rechargeable batteries through T.1 to T.5, with rechargeable adding T.7.
